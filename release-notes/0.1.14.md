# iFaceMatch Customer Hosted 0.1.14 — Console login recovery

Status: **candidate, not yet signed or published**.

## Changes

- Fix the login CSRF nonce rotating across repeated GET requests.
- Keep the favicon route from creating a login redirect or replacing CSRF cookies.
- Add regression coverage for HTTP IPv4 commercial login, repeated GET and invalid token rejection.
- Include the new signed `ifacematchctl upgrade-console` command with preflight, isolated Console restart and rollback.
- Preserve the signed 0.1.10 Server, Secure Core, Model Pack and Web SDK binaries and component versions.

## Release lineage

The deployment baseline on the `cargodev` host is the signed **0.1.10** release. Version `0.1.11` was published for a different pilot and **must not be overwritten or repurposed**. This candidate is an independent `0.1.10 → 0.1.14` Console-only upgrade, rather than a repackaging of published 0.1.11.

The only approved modified signed artifact paths, relative to the verified 0.1.10 baseline, are:

- `console/ifacematch-console`
- `bin/ifacematchctl`
- `console/BUILD_PROVENANCE.txt`

No changes to the signed inventory, Server binary, native libraries, Model Pack, SDK, customer data, license or operator database are allowed. The new version is signed by the existing authorized Ed25519 distribution identity.

## Packaging

On FACTORYAPPS, in the coordinator repository at the reviewed release branch:

```bash
make test
make release-base
make release VERSION=0.1.14
make release-verify VERSION=0.1.14
```

The build requires the pinned signed 0.1.10 archive, local production signing authority and the immutable Git commits in `versions.lock.json`. It refuses an existing output folder and rejects unapproved artifact changes.

## Distribution and activation

**Do not use the published 0.1.11 updater**: it is bound to the other pilot host. The reviewed Portal `upgrade.sh --component console` integration supports the new `upgrade-console` CLI, but customer release authorization and Central distribution remain separate gates.

Before production apply:

1. Verify the new archive SHA-256 and pinned Ed25519 signature.
2. Test the new Console-only CLI with `--dry-run` against the signed release on the target host.
3. Obtain a recoverable external backup and approve the maintenance window.
4. Activate **only** `ifacematch-console.service` through the verified upgrade CLI; check `/login`, stable CSRF, existing SDK routes, Server `/health` and a real operator login.
5. Preserve the original 0.1.10 release and private rollback backup.

Avoid routine authentication over public HTTP: this deployment currently serves passwords without TLS.
